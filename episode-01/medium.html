Why Data Cleaning Is Episode 1

Not "What Is a Neural Network." Not "How Transformers Work." Data cleaning.

Here's an uncomfortable truth about AI work: 80% of a real AI project is data preparation. The model is the easy part.

Every AI project you'll ever work on — training a chatbot, building a recommendation engine, fine-tuning an LLM — starts with the same boring, unglamorous step: getting your data into shape.

If your data has duplicates, your model learns the same example twice and thinks it's more important than it is. If your data has missing values, your training crashes or your model learns garbage. If your headers are inconsistent, your pipeline breaks at 2 AM.

I could have started this series with neural networks or attention mechanisms. But that would be like teaching someone to cook by starting with molecular gastronomy. First, you learn to wash the vegetables, sharpen the knife, and keep your kitchen clean.

Episode 1 is the kitchen.

What We're Building

We are building a Python command-line tool with two commands, running entirely inside Docker.

The Clean Command: Takes a messy CSV file and fixes it. Normalizes headers, trims whitespace, removes duplicates, handles missing data, saves a clean CSV, and prints a JSON report.

The Run-Notebook Command: Executes a Jupyter notebook without opening a browser. Runs every cell programmatically, saves the executed notebook with all outputs, and reports timing and errors.

None of this is glamorous. All of it is essential. Let's build it.

Step 1: The Project Structure (And The Rule of Raw Data)

Every well-organized Python project looks roughly the same. If you clone a machine learning repo from GitHub, you'll see this pattern:

  • data/raw/ — Untouched source data. Training data, downloaded datasets.
  • data/cleaned/ — Processed output. Feature-engineered data ready for models.
  • notebooks/ — Exploration, analysis, and experiments.
  • src/ — Reusable Python modules and utilities.
  • logs/ & tests/ — Execution records and automated tests.

The most important rule in AI engineering: Separate your raw and cleaned data directories.

Why? Because in AI work, you never modify your source data. Your raw training data is sacred. You always read from raw/, transform it, and write to cleaned/. If something goes wrong, your original data is untouched.

Step 2: The Messy Data

We need data that's broken in realistic ways. I created a sample CSV with 12 rows and 8 deliberate problems:

  • Headers have extra spaces: The column isn't "Name" — it's " Name " with invisible spaces.
  • Values have whitespace padding: "Bob Smith" and " Bob Smith " look like different people to standard deduplication algorithms.
  • Duplicate rows: Two customers appear twice. Your model is subtly biased and you don't know why.
  • Missing values everywhere: Blank ages, missing emails. Feed this to a model and you get NaN errors and crashed training runs.

If you fed this directly to a model, you'd get garbage. "Garbage in, garbage out" isn't a cliché in AI — it's a law of physics.

Step 3: The Data Cleaner

We build a Python module (src/cleaner.py) with small, focused functions that each fix one problem.

  • clean_headers() takes " Name " and turns it into name. Lowercases everything and replaces spaces with underscores.
  • trim_strings() loops through text columns and strips leading/trailing whitespace.
  • drop_duplicates() finds exact duplicate rows and removes them.
  • handle_missing() deals with blanks using two strategies: either "drop" the row entirely, or "fill" them with averages and defaults.

Why small functions instead of one big one? Because in real AI work, you constantly swap out individual steps. Next week you might want to handle missing values differently. Small, composable steps are the secret to scalable AI pipelines.

Step 4: The Notebook Runner

Jupyter notebooks are great for exploration. They're terrible for automation. You can't put "open browser, click Run All, wait, check output" in an automated CI/CD pipeline.

The solution: execute notebooks programmatically using a Python library called nbclient (src/notebook_runner.py).

Imagine you're training models. After each training run, you want a notebook that loads predictions, calculates accuracy, and saves an HTML report. You don't want to manually open that notebook every time. You want an automated script to trigger it. That is what this module does.

Step 5: Containerize Everything with Docker

You need Docker Desktop installed. That's it.

Python? Inside Docker. Pandas? Inside Docker. Jupyter? Inside Docker.

You don't install a single Python package on your Mac. Everything lives in the container. This is how real AI teams work — and it's why "works on my machine" stops being a problem.

By using Docker Volumes, we map our local data and code folders directly into the container. This means when the container creates the clean CSV, it immediately appears on your Mac's filesystem.

We wrap it all up in a Makefile so we never have to type long Docker commands:

run-clean:
    docker compose run --rm cli clean \
        /workspace/data/raw/customers.csv \
        /workspace/data/cleaned/customers_clean.csv \
        --missing drop --json

run-notebook:
    docker compose run --rm cli run-nb \
        /workspace/notebooks/analyze_customers.ipynb

run-all: run-clean run-notebook

Run It

Type make run-all and watch the pipeline do its job.

  1. It spins up the Python container.
  2. It ingests the messy 12-row CSV.
  3. It drops duplicates, fixes string formatting, and drops rows with missing data.
  4. It saves a perfect, 5-row clean dataset to your local machine.
  5. It immediately spins up the Jupyter Notebook, ingests the clean data, runs an analysis, and saves the executed notebook with charts and outputs.

One command. Complete automation.
